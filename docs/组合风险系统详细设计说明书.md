## 1. 设计目标与原则

### 1.1 设计目标

1. 将对公信贷业务数据组织为客户、额度、申请、合同、债项、押品和风险结果的完整链路。
2. 支持组合、客户、合同和债项多层级风险查询及下钻。
3. 将 PD、LGD、EAD、EL、集中度、限额和预警作为统一风险对象管理。
4. 保证风险计算结果带数据日期、模型版本、计算批次和证据。
5. 保证预警案件、风险台账、整改任务、风险事件和指标形成闭环。
6. 通过微服务、配置中心、熔断降级和监控提升可维护性。
7. 通过统一认证、接口鉴权、操作审计和敏感数据保护满足安全要求。

### 1.2 设计原则

| 原则 | 设计要求 |
| --- | --- |
| 业务口径集中 | 核心计算在后端服务完成，前端只负责交互与展示 |
| 历史可追溯 | 模型、限额、回溯、压力测试和效果评价保留历史批次 |
| 关联优先 | 所有风险结果必须能下钻至客户、合同、债项或源记录 |
| 服务自治 | 服务拥有清晰职责，通过接口或消息协作 |
| 失败隔离 | 外部数据、邮件和消息故障不得拖垮核心查询 |
| 最小权限 | 页面、按钮和接口同时进行权限控制 |
| 配置外置 | 环境参数通过 Apollo 和环境变量管理 |
| 可观测 | 请求、异常、任务、资源和外部调用可监控 |
| 可演进 | 新模型、新指标和新场景通过版本和参数扩展 |

### 1.3 当前规模基线

当前数据库共 54 张表，其中系统管理表 15 张、对公信贷核心表 12 张、风险管理表 27 张；包含 29 个唯一键、41 个外键和 30 个检查约束。system-service 当前包含 28 个 Controller、27 个 Service 实现、12 个 Mapper 接口、12 个 Mapper XML 和 17 个 Vue 页面。

## 2. 总体架构设计

### 2.1 逻辑架构

系统分为六层：

| 层级 | 组件 | 职责 |
| --- | --- | --- |
| 展示层 | Vue 3、Element Plus | 页面、图表、筛选、下钻和交互 |
| 接入层 | API Gateway | 路由、令牌校验、会话校验、请求追踪、跨域 |
| 业务服务层 | Auth、User、System Service | 认证、权限、组合风险业务 |
| 领域与数据访问层 | Service、Scoring Engine、Mapper、MyBatis XML | 业务编排、算法和 SQL |
| 基础设施层 | MySQL、Redis、RocketMQ、Eureka、Apollo | 数据、会话、消息、发现和配置 |
| 运维层 | Actuator、Prometheus、Grafana、Dozzle | 健康、指标、告警和日志 |

请求主路径为：

浏览器 → frontend → api-gateway → auth-service / user-service / system-service → MySQL / Redis / RocketMQ。

配置与治理路径为：

后端服务 → Eureka 注册；后端服务 ← Apollo 配置；Prometheus → 各服务指标；Grafana → Prometheus。

### 2.2 微服务划分

| 服务 | 端口 | 主要职责 | 数据依赖 |
| --- | --- | --- | --- |
| discovery-server | 8761 | Eureka 注册中心 | 无业务数据 |
| api-gateway | 8088 | API 路由、认证前置、会话校验、用户头传递 | Redis |
| auth-service | 9001 | 登录、退出、验证码、密码重置、令牌签发 | MySQL、Redis |
| user-service | 9002 | 用户、角色、权限、部门、岗位、菜单 | MySQL、Redis |
| system-service | 9003 | 组合风险、信贷查询、LGD、限额、预警、AI、治理和报表 | MySQL、Redis、RocketMQ、外部接口 |
| frontend | 5173 | 风险运营工作台 | API Gateway |

### 2.3 服务依赖规则

- 前端不得直接访问业务服务，只访问 API Gateway。
- api-gateway 根据 URL 前缀路由到 user-service 或 system-service。
- auth-service 签发 JWT 并维护会话。
- user-service 和 system-service 使用公钥验签，不应持有生产私钥。
- system-service 通过 OpenFeign 调用 user-service 内部目录接口和外部风险数据接口。
- OpenFeign 启用熔断降级；外部接口失败返回本地分析结果。
- 服务不得通过共享 Java 对象直接耦合，公共响应和安全组件位于 common 模块。

## 4. 通用框架设计

### 4.1 统一响应

后端响应使用 ApiResponse<T>：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| code | int | 0 表示成功，401/403/500 等表示失败 |
| message | String | success 或错误摘要 |
| data | T | 业务数据 |
| timestamp | Instant | 服务响应时间 |

分页响应使用 PageResult，业务列表应返回数据集合、总数、页码和每页数量。

### 4.2 请求追踪

- GatewayRequestTraceFilter 生成或传递 X-Request-Id。
- 下游服务日志和错误日志使用同一请求标识。
- 操作日志记录用户、模块、动作、方法、状态和时间。
- 外部服务调用日志应记录请求标识，便于链路排查。

### 4.3 统一异常处理

GlobalExceptionHandler 捕获未处理异常，写入 sys_error_log，并返回统一失败响应。详细设计要求：

- 参数错误使用 400 类业务响应，不应全部转为 500。
- 未认证由过滤器返回 401。
- 权限不足由 PermissionInterceptor 返回 403。
- 业务对象不存在、状态冲突和唯一键冲突应返回明确业务码。
- 响应不得包含 SQL、密钥、完整堆栈和敏感数据。
- 错误日志写入失败不得覆盖原始异常。

### 4.4 通用 CRUD

通用台账模块继承 CrudControllerSupport 和 AbstractSystemCrudService，适用于风险台账、评估、控制、整改、事件、指标、通知、配置和日志查询。专业风险页面使用独立 Controller 和 Service，避免复杂聚合逻辑进入通用 CRUD。

## 5. 安全架构详细设计

### 5.1 认证时序

1. 前端提交账号、密码和验证码至 /api/auth/login。
2. Gateway 将公开登录路径转发到认证入口。
3. auth-service 查询用户、角色和权限。
4. AuthServiceImpl 校验密码及状态，生成 tokenId。
5. JwtService 使用 RSA 私钥签名令牌，令牌包含用户、角色、权限和租户。
6. TokenSessionService 将 tokenId 会话写入 Redis。
7. 前端保存令牌，后续请求携带 Authorization: Bearer。

### 5.2 网关认证

JwtAuthFilter 的处理顺序：

1. OPTIONS、登录、退出、验证码、密码重置和 actuator 路径放行。
2. 非 /api 路径不进入 API 认证。
3. 检查 Bearer 令牌。
4. 提取 tokenId 和 username。
5. 校验并刷新 Redis 会话。
6. 对加密令牌进行验证并转换为下游签名令牌。
7. 设置 Authorization 和 X-Auth-Username 请求头。
8. 失败返回 401。

### 5.3 服务端二次认证

ServletAuthFilter 在 user-service 和 system-service 中执行：

- 公共或 internal 路径按白名单处理。
- 解析下游 Bearer 令牌。
- 校验 Redis 会话并刷新有效期。
- 解析 AuthContext，并放入 request attribute。
- 无令牌、会话过期和令牌无效分别返回 401。

### 5.4 权限拦截

RequirePermission 可标注在 Controller 类或方法上。PermissionInterceptor 读取 AuthContext 中的权限集合，匹配成功后放行，否则返回 403。前端 router.beforeEach 同时检查路由 meta.permission，用于用户体验；服务端检查是最终安全边界。

### 5.5 生产安全加固

| 项目 | 当前开发设计 | 生产要求 |
| --- | --- | --- |
| RSA 密钥 | 支持配置默认值 | 私钥必须移出源码和镜像，只在 auth-service 安全注入 |
| 数据库密码 | 支持环境默认值 | 使用密钥系统或受控环境变量，不得使用默认密码 |
| JWT 有效期 | 默认 86400 秒 | 按安全策略设置并支持主动失效 |
| 会话有效期 | 默认 900 秒 | 结合业务操作时长与风险确定 |
| CORS | 本地 localhost | 配置生产域名白名单 |
| HTTPS | 本地可使用 HTTP | 生产必须启用 TLS |
| 敏感字段 | 数据库含加密及哈希字段 | 页面脱敏、按权查看、导出审批 |
| internal 接口 | 使用内部路径 | 生产应限制网络边界并增加服务身份校验 |

## 6. 网关与服务治理设计

### 6.1 路由设计

| 路由 | 目标服务 | 处理 |
| --- | --- | --- |
| /api/users、roles、permissions、departments、posts、menus | user-service | StripPrefix=1 |
| /api/risks、logs、notifications、configs、security、tenants、import、export | system-service | StripPrefix=1 |
| /api/auth | 认证入口 | 由认证服务或本地认证控制器处理 |

### 6.2 服务发现

应用服务向 Eureka 注册，默认注册地址为 discovery-server:8761/eureka。Docker 环境通过环境变量覆盖 localhost。Eureka 主要用于服务发现和运行状态查看；当前网关路由同时支持显式 URI，生产可根据部署方式切换到负载均衡 URI。

### 6.3 Apollo 启动保护

- 各服务配置 app.id 和 Apollo Meta 地址。
- bootstrap eagerLoad 在 Spring 上下文初始化前加载配置。
- ApolloStartupGuard 在 required 模式下阻止缺少关键配置的服务启动。
- 命名空间按 application、database、security、gateway、risk、mq 划分。
- 运行参数优先由 Apollo 或环境变量覆盖本地默认值。

### 6.4 OpenFeign 与熔断

system-service 定义：

- UserDirectoryClient：调用 user-service 获取启用用户目录。
- ExternalRiskDataClient：调用外部企业风险数据。
- UserDirectoryClientFallbackFactory：用户服务不可用时使用本地目录降级。
- ExternalRiskDataClientFallbackFactory：外部数据不可用时返回 UNAVAILABLE。

external-risk-data 客户端连接超时 3000 毫秒，读取超时 6000 毫秒。Spring Cloud OpenFeign circuitbreaker.enabled=true，避免外部故障占满线程。

## 7. 核心领域模块设计

### 7.1 组合风险总览

| 组件 | 职责 |
| --- | --- |
| CompositeRiskDashboardController | GET 总览、POST 创建处置 |
| CompositeRiskDashboardService | 总览和客户评分接口 |
| CompositeRiskDashboardServiceImpl | 聚合客户特征、调用评分、生成预警视图 |
| CompositeRiskDashboardMapper | 查询组合、客户、行业、产品和风险特征 |
| CompositeRiskScoringEngine | 根据动态规则输出评分、等级、标签和预测 |

处理流程：

1. Mapper 获取客户维度风险特征。
2. Service 加载启用的 risk_scoring_rule。
3. ScoringEngine 对每个客户执行规则。
4. Service 聚合风险等级、行业、产品和预警客户。
5. Controller 返回统一响应。

### 7.2 动态评分引擎

基础分为 10 分。规则字段包括 metric_key、threshold_value、operator_type、effect_type、score_value、risk_tag 和 reason_template。

| effect_type | 处理 |
| --- | --- |
| ADD | 当前评分增加 score_value；同一指标只执行一次 ADD |
| FLOOR | 当前评分不低于 score_value |

支持操作符 GT、GTE、LT、LTE、EQ。评分最高为 100。

风险等级：

| 分数 | 风险等级 | 优先级 |
| --- | --- | --- |
| 85 至 100 | 极高风险 | P1 |
| 65 至 84 | 高风险 | P2 |
| 45 至 64 | 中风险 | P3 |
| 0 至 44 | 低风险 | P4 |

预测加分：

| 特征 | 条件 | 加分 |
| --- | --- | --- |
| 存在逾期 | overdue_count > 0 | 8 |
| PD 较高 | max_pd ≥ 5% | 6 |
| 额度高占用 | utilization_rate ≥ 90% | 4 |
| 押品覆盖不足 | coverage_rate < 50% | 5 |

预测加分上限 20，当前评分达到 85 时不再增加。

预警类型按名单风险、债项违约、严重逾期、逾期、评级触发、PD 高风险、额度高占用和组合预警顺序识别。

### 7.3 信贷综合查询

| 组件 | 职责 |
| --- | --- |
| CreditDomainQueryController | 解析关键字、维度、状态、日期和分页参数 |
| CreditDomainQueryCriteria | 封装查询条件 |
| CreditDomainQueryServiceImpl | 条件规范化、总数和列表查询、客户 360 组织 |
| CreditDomainQueryMapper | 12 表查询、分类统计和时间轴 SQL |

查询模式：

- 客户模式：以 corporate_customer 为主表。
- 合同模式：以 corporate_credit_contract 为主表。
- 债项模式：以 corporate_credit_drawdown 或 exposure 为主表。
- 风险模式：以 overdue、debt_default、customer_default 和 exposure 为主表。

时间轴设计：

| 事件 | 排序权重 |
| --- | --- |
| 业务申请 | 10 |
| 合同 | 20 |
| 债项支用 | 30 |
| 风险敞口计量 | 40 |
| 逾期 | 50 |
| 债项违约 | 60 |
| 客户违约 | 70 |

先按业务日期升序，再按排序权重升序；同类事件按业务编号稳定排序。日期修复和数据质量校验保证合同先于支用、支用先于逾期。

### 7.4 风险台账

RiskLedgerController → RiskLedgerServiceImpl → RiskLedgerMapper。

台账以客户编号分组，聚合有效评级、额度、申请、合同、支用、押品、敞口、逾期、债项违约和客户违约。SQL 对一对多表先分别聚合，再连接客户主表，避免多表直接连接导致金额重复。

台账结果包含：

- 最新评级和评级等级。
- 当前有效额度及可用金额。
- 申请、合同、支用和押品数量及最新编号。
- 未结本金、总敞口和担保金额。
- 逾期数量、最大逾期天数。
- 债项违约数量、最高违约等级。
- 客户违约状态。
- 综合台账风险等级。

### 7.5 违约趋势

CreditDefaultTrendController → CreditDefaultTrendServiceImpl → CreditDefaultTrendMapper。

按日期聚合逾期、债项违约和客户违约新增量。日期维度由请求范围生成，缺失日期补零，保证柱状图和折线图连续。筛选条件包括客户、行业、产品、机构和风险等级。

### 7.6 LGD 风险管理

| 组件 | 职责 |
| --- | --- |
| RiskLgdController | 总览、台账、债项、客户、治理、计算和压力测试接口 |
| RiskLgdServiceImpl | 组合汇总、债项明细、批次计算、压力场景 |
| RiskLgdMapper | LGD 参数、敞口、押品、违约和损失 SQL |

核心计算：

- 加权 LGD 平均值 = Σ(EAD × LGD 平均值) ÷ ΣEAD。
- 加权 LGD 衰退值 = Σ(EAD × LGD 衰退值) ÷ ΣEAD。
- EL 平均值 = PD × LGD 平均值 × EAD。
- EL 衰退值 = PD × LGD 衰退值 × EAD。
- 押品覆盖率 = 有效押品担保价值 ÷ EAD。
- 产品回收率由产品、押品、历史回收或模型参数确定。

模型版本、分段参数、计算批次和压力测试分别保存，避免覆盖历史。定时计算默认每日 08:10。

### 7.7 组合集中度与限额

RiskPortfolioManagementController → RiskPortfolioManagementServiceImpl → RiskPortfolioMapper。

总览返回 summary、industry_concentration、product_concentration、organization_concentration、top_customers、limit_monitor、latest_backtest 和 latest_effectiveness。

集中度：

- 行业、产品和机构按有效 exposure_status=ACTIVE 的敞口聚合。
- 统计 exposure_count、customer_count、EAD、EL 平均值和 EL 衰退值。
- 行业 HHI = Σ(行业 EAD ÷ 组合 EAD)²。

限额初始化：

- 对行业、产品和机构分别创建 EAD 与 EL_DOWN 两类限额。
- 仅在没有人工限额且实际值大于 0 时创建。
- 初始限额 = 当前实际值 × 130%。
- 默认预警比例 = 80%。

限额状态：

| 条件 | 状态 |
| --- | --- |
| 限额停用 | DISABLED |
| 利用率 > 100% | BREACH |
| 利用率 ≥ 预警比例 | WARNING |
| 其他 | NORMAL |

每日快照按 limit_id + data_date 唯一，使用 upsert 保证任务重跑幂等。

### 7.8 PD/LGD/EAD 回溯

回溯批次编号格式为 BT-yyyyMMddHHmmss。数据日期取风险敞口最大 data_date。

回溯维度：

- PRODUCT：按 product_type 分段。
- INDUSTRY：按客户行业分段。

计算字段：

| 字段 | 公式 |
| --- | --- |
| expected_pd | EAD 加权 PD |
| observed_default_rate | 违约债项数 ÷ 观察债项数 |
| expected_lgd | EAD 加权 LGD |
| observed_lgd | 损失金额 ÷ 实际违约暴露 |
| predicted_default_ead | 预测发生违约的 EAD |
| observed_default_ead | 债项违约表实际违约暴露 |
| pd_bias | observed_default_rate - expected_pd |
| lgd_bias | observed_lgd - expected_lgd |
| ead_bias | (observed EAD - predicted EAD) ÷ predicted EAD |

校准状态阈值：

| 参数 | WATCH | RECALIBRATE |
| --- | --- | --- |
| PD 绝对偏差 | ≥ 0.015 | ≥ 0.030 |
| LGD 绝对偏差 | ≥ 0.050 | ≥ 0.100 |
| EAD 绝对偏差 | ≥ 0.080 | ≥ 0.150 |

任一参数达到较高阈值即为 RECALIBRATE；未达到高阈值但任一达到关注阈值为 WATCH；其余为 STABLE。

### 7.9 预警案件闭环

RiskGovernanceController → RiskGovernanceServiceImpl → RiskGovernanceMapper。

案件刷新：

1. 获取当前客户评分。
2. 评分低于 45 不创建预警。
3. 检查客户是否已有未关闭案件。
4. 无案件时新建 risk_alert_case；有案件时更新风险分、信号和优先级。
5. 建立案件与客户、台账和风险证据的关联。

案件启动：

- 状态更新为 IN_PROGRESS。
- 创建或关联 risk_register。
- 创建 risk_treatment_plan，保存责任人、措施、期限和状态。
- 同步 risk_indicator 和 risk_event。
- risk_alert_case_link 保存 ALERT_CASE、REGISTER、TREATMENT、INDICATOR、EVENT 等关系。

案件关闭：

- 校验案件存在且允许关闭。
- 更新 alert_state、closed_at、closed_by 和 closure_comment。
- 将关联整改任务更新为完成或复核状态。
- 回写风险台账、事件和指标状态。
- 保留关闭时风险评分，作为效果评价基线。

### 7.10 预警处置效果评价

评价对象为 RESOLVED 且 closed_at 非空的案件。

| 条件 | 状态 |
| --- | --- |
| 关闭不足 30 天 | OBSERVING |
| 当前评分 ≤ 基准评分 - 15，且逾期数和违约数均为 0 | EFFECTIVE |
| 当前评分低于基准评分，但未满足全部有效条件 | PARTIAL |
| 其他 | INEFFECTIVE |

评价快照保存案件、评价日期、观察窗口、基准和当前评分、PD、LGD、逾期、违约、状态、结论和评价人。唯一键保证同一案件同日只保留一条评价。

## 8. 数据库详细设计

### 8.1 数据库规范

- 引擎使用 InnoDB。
- 字符集使用 utf8mb4，排序规则使用 utf8mb4_0900_ai_ci。
- 主键使用 bigint unsigned 自增。
- 业务表包含 tenant_id。
- 业务编号使用唯一键。
- created_at、updated_at 记录审计时间。
- deleted_flag 实现逻辑删除。
- 状态字段使用 varchar，值域由检查约束和服务校验共同控制。
- 金额使用 decimal(18,2) 或高精度 decimal。
- 概率和比率使用 decimal(10,6)。
- 历史计算使用 data_date、run_code 或 version_no 标识。

### 8.2 表分区

| 分区 | 表数量 | 主要对象 |
| --- | --- | --- |
| sys_* | 15 | 租户、用户、权限、菜单、日志、通知、配置、安全策略 |
| corporate_* | 12 | 对公信贷完整业务链 |
| risk_* | 27 | 风险台账、评分、预警、模型、LGD、限额、回溯和治理 |

### 8.3 核心实体关系

corporate_customer 1→N corporate_rating，但有效记录业务约束为 1。  
corporate_customer 1→N corporate_credit_limit，但有效记录业务约束为 1。  
corporate_credit_limit 1→N corporate_credit_application。  
corporate_credit_application 1→1 corporate_credit_contract。  
corporate_credit_contract 1→N corporate_credit_drawdown。  
corporate_credit_contract N↔N corporate_credit_collateral，通过 corporate_credit_contract_collateral。  
corporate_credit_drawdown 1→N corporate_credit_overdue。  
corporate_credit_drawdown 1→N corporate_risk_exposure 历史记录，当前有效记录按数据日期和状态识别。  
corporate_credit_drawdown 1→0..1 有效 corporate_debt_default。  
corporate_customer 1→0..1 有效 corporate_customer_default。

### 8.5 有效记录唯一性

数据库保存历史评级和额度，Service/SQL 以状态、有效期和 deleted_flag 筛选当前有效记录。生产增强建议增加能够表达“每客户仅一条有效记录”的约束策略，可采用：

- 状态转换事务中先关闭旧记录再启用新记录。
- 使用生成列和唯一索引。
- 使用单独 current 表或有效记录映射表。
- 在批量导入后执行一致性检查。

### 8.6 风险敞口设计

corporate_risk_exposure 是组合计量事实表，粒度为客户 + 合同 + 债项 + 数据日期 + 场景。关键字段：

- exposure_balance、ead_amount、undrawn_amount。
- collateral_value、guaranteed_amount。
- lgd_avg、lgd_downturn、pd。
- el_avg、el_downturn。
- rating_result、product_recovery_rate、five_category。
- overdue_days、default_flag、risk_level。
- model_name、model_version、scenario_type。
- measurement_date、data_date、exposure_status。

当前组合查询只统计 deleted_flag=0 且 exposure_status=ACTIVE。历史数据通过 data_date 和状态保留。

### 8.7 违约设计

债项违约等级：

- A：逾期天数大于 90。
- B：五级分类为次级、可疑或损失。
- C：评级结果为 21。

corporate_debt_default 同时保存三个触发标志，避免只保留最终等级而丢失原因。corporate_customer_default 由有效债项违约按客户聚合，保存首次、最新日期、最高等级、违约债项数量、违约暴露、回收和损失。

- 金额统一千分位和两位小数；概率统一百分比。
- 数据日期与更新时间固定显示。
- 表格长文本使用省略和 tooltip，编号可复制。
- 移动宽度下优先保证查询、指标和表格可横向滚动，不压缩关键文字。

## 15. 性能与容量设计

### 15.1 查询优化

- 所有列表分页。
- 客户编号、合同编号、债项编号、状态和数据日期建立索引。
- 多个一对多表先聚合再连接，避免笛卡尔放大。
- 组合总览优先读取当前有效敞口和每日快照。
- 图表按日期范围限制查询，长周期使用日/月汇总表。
- 排序字段白名单化，避免索引失效和 SQL 注入。

### 15.2 缓存设计

当前 Redis 主要用于会话。生产可缓存：

- 用户权限和菜单，短 TTL，权限变更主动失效。
- 风险字典和配置。
- 组合总览短时缓存。
- 外部风险数据在授权允许范围内按客户短时缓存。

不得缓存未经权限隔离的敏感客户详情。缓存键需包含 tenantId、用户权限范围或业务对象。

### 15.3 容量规划

建议以 100 万条有效/历史风险敞口、10 万客户、100 并发用户为首轮生产压测基线。重点验证：

- 组合总览 P95。
- 客户 360 P95。
- 台账分页和导出。
- 每日限额、LGD、回溯和质量任务总耗时。
- 数据库 CPU、临时表、慢 SQL 和连接池。

## 16. 一致性、幂等与并发设计

### 16.1 幂等键

| 场景 | 幂等键 |
| --- | --- |
| 限额快照 | limit_id + data_date |
| 效果评价 | alert_case_id + evaluation_date |
| 合同押品关系 | contract_no + collateral_no |
| 回溯分段 | run_code + segment_type + segment_code |
| 预警案件 | customer_no + 未关闭状态 + 风险类型 |
| 客户违约汇总 | customer_no + data_date 或当前有效状态 |

### 16.2 并发控制

- 限额修改使用事务，必要时对记录加版本号实现乐观锁。
- 模型发布必须锁定模型或使用状态条件更新，防止并发发布。
- 案件启动和关闭使用当前状态作为更新条件。
- 定时任务在集群环境使用分布式锁。
- 批量导入通过业务唯一键和错误清单处理重复。

### 16.3 最终一致性

数据库内闭环对象使用同一事务保证强一致。通知和外部调用使用最终一致性：

- 先提交业务事务。
- 再发布消息。
- 发布失败记录补偿状态。
- 消费端幂等。

生产建议引入 outbox 表，避免事务提交后消息丢失。

## 18. 发布与回滚设计

### 18.1 构建

- Maven Reactor 构建 common 和各后端服务，Java 17。
- Vite 构建前端静态产物。
- backend/Dockerfile 按 SERVICE_NAME 复制对应 JAR。
- frontend/Dockerfile 复制 dist 和静态服务器。
- 镜像使用语义版本或构建号，不应长期只覆盖 1.0.0。

### 18.2 数据库迁移

- database/init.sql 用于全新环境。
- composite_risk_phase2 至 phase8 用于增量升级。
- 迁移前备份数据库。
- DDL 使用 IF NOT EXISTS 等方式提高可重复性。
- 生产建议引入 Flyway 或 Liquibase 记录 schema_version。

### 18.3 发布顺序

MySQL/Redis/RocketMQ/Apollo → discovery-server → auth-service/user-service/system-service → api-gateway → frontend → Prometheus/Grafana → 烟雾测试。

### 18.4 回滚

- 保留上一版本镜像。
- 应用回滚使用 Docker 镜像标签。
- 数据库新增表和新增列通常保留，避免破坏历史数据。
- 破坏性 DDL 必须提供反向脚本和数据恢复方案。
- 模型和限额通过版本/历史记录回滚，不直接覆盖。
