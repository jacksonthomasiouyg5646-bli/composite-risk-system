## 1. 引言

### 1.1 建设背景

组合风险管理需要同时观察客户、评级、额度、业务申请、合同、债项支用、押品、风险敞口、逾期、债项违约和客户违约等数据。传统分散查询方式难以回答以下管理问题：

- 当前组合风险总量、预期损失和压力损失是多少。
- 风险是否集中在特定行业、产品、机构或客户。
- PD、LGD、EAD 参数是否与实际违约和损失表现一致。
- 一笔预警从识别、立案、整改到关闭是否形成完整闭环。
- 预警关闭后客户风险是否真正下降。
- 管理人员能否快速获得有证据支撑的客户风险结论。
- 数据、模型、限额和人工操作是否可追溯、可审计。

组合风险系统以信贷域完整数据链为基础，将风险计量、组合监控、预警处置、模型治理、数据治理和智能分析集中到同一平台，形成“数据采集—风险识别—计量评估—预警立案—任务整改—效果评价—模型反馈”的管理闭环。

### 1.2 建设目标

系统应实现以下目标：

1. 建立统一、可信、可追溯的组合风险数据底座。
2. 建立客户、合同、债项、押品和风险敞口的全链路关联。
3. 实现 PD、LGD、EAD、EL 等核心风险参数的展示、计算、回溯与校准。
4. 实现行业、产品、机构和客户维度的集中度及限额管理。
5. 实现逾期、违约、评级恶化、LGD 上升等风险信号的自动预警。
6. 实现预警案件、风险台账、整改任务、风险指标和风险事件的自动关联。
7. 实现处置效果评价，并将评价结果反馈到限额、评分和模型治理。
8. 提供严谨、易用、可视化的管理页面，支持查询、分析、下钻和导出。
9. 提供统一权限、审计、配置、监控和容灾能力。
10. 在外部数据不可用时保持本地风险分析连续可用。

### 1.3 适用范围

本期范围包括：

- 对公信贷客户及其评级、额度、申请、合同、债项、押品数据。
- 风险敞口、逾期、债项违约、客户违约数据。
- 组合看板、信贷综合查询、风险台账、违约趋势、LGD 管理。
- 组合集中度、限额监测、PD/LGD/EAD 回溯校准。
- 评分规则、模型版本、模型审批、模型监控和压力测试。
- 预警订阅、预警案件、风险台账、整改任务、风险事件、风险指标。
- 预警处置效果评价。
- AI 客户风险分析、智能问答和外部企业风险数据接入。
- 数据质量、数据血缘、审计日志、系统配置、通知和运维监控。

- 核心账务、会计核算和实际放款记账。
- 法律诉讼系统、征信系统和外部数据供应商内部功能。
- 独立的资本计量引擎和监管报送平台。
- 自动代替人工完成授信审批或最终违约认定。

### 1.5 术语

| 术语 | 含义 |
| --- | --- |
| PD | Probability of Default，违约概率 |
| LGD | Loss Given Default，违约损失率 |
| EAD | Exposure at Default，违约风险暴露 |
| EL | Expected Loss，预期损失，通常为 PD × LGD × EAD |
| LGD 平均值 | 基准或正常经济环境下的违约损失率 |
| LGD 衰退值 | 压力或经济衰退场景下的违约损失率 |
| HHI | 赫芬达尔指数，用于衡量组合集中度 |
| 债项 | 在合同项下形成的具体信贷支用及还款义务 |
| 风险敞口 | 以客户、合同、债项为基础形成的风险计量记录 |
| 预警案件 | 由风险信号形成、需要调查和处置的工作对象 |
| 回溯校准 | 将模型预测值与实际违约、损失或暴露结果进行比较并形成调整建议 |

## 2. 系统总体说明

### 2.1 系统定位

组合风险系统定位为对公信贷组合风险管理与决策支持平台。系统不替代信贷业务系统，而是汇聚信贷业务数据，形成组合层、客户层、合同层和债项层的风险视图，为风险监控、预警处置、模型管理和管理决策提供支持。

### 2.2 总体业务能力

| 能力域 | 主要能力 |
| --- | --- |
| 风险数据底座 | 客户、评级、额度、申请、合同、债项、押品、敞口、逾期、违约数据统一关联 |
| 组合风险洞察 | 总敞口、EL、压力 EL、风险客户、集中度、违约趋势、行业和产品分布 |
| 风险计量 | PD、LGD、EAD、回收率、EL、压力情景、模型版本和计算批次 |
| 限额管理 | 行业、产品、机构、客户维度限额维护、占用监测、预警和超限识别 |
| 预警闭环 | 信号识别、案件生成、台账关联、任务整改、状态回写、指标和事件同步 |
| 模型治理 | 规则维护、版本审批、模拟、发布、回滚、监控和回溯校准 |
| 智能分析 | 客户风险分析、证据链、智能问答、外部数据增强和降级 |
| 治理审计 | 数据质量、血缘、操作日志、登录日志、错误日志、安全策略和配置管理 |

### 2.3 系统架构

系统采用前后端分离和微服务架构：

1. 浏览器访问 Vue 3 前端。
2. 前端通过 API Gateway 统一访问后端。
3. Auth Service 负责登录、令牌签发和会话管理。
4. User Service 负责用户、角色、权限、部门、岗位和菜单。
5. System Service 负责组合风险全部业务功能。
6. Eureka 负责服务注册与发现。
7. Apollo 负责应用、数据库、安全、风险和消息配置。
8. MySQL 保存业务数据、风险结果和审计数据。
9. Redis 保存会话及缓存信息。
10. RocketMQ 承担通知和异步消息。
11. Prometheus、Grafana 和日志查看器提供运行监控。
12. 外部企业风险数据通过 OpenFeign 调用，并使用熔断降级保护本地分析。

架构逻辑如下：

浏览器 → 前端 → API Gateway → Auth Service / User Service / System Service  
System Service → MySQL / Redis / RocketMQ / 外部风险数据服务  
全部后端服务 → Eureka / Apollo / Prometheus

## 4. 核心业务流程

### 4.1 信贷业务数据链

业务时间顺序必须遵循：

客户建立 → 客户评级/额度生效 → 业务申请 → 合同签订并生效 → 债项支用 → 风险敞口计量 → 到期/逾期 → 债项违约 → 客户违约汇总。

关联规则如下：

| 上游对象 | 下游对象 | 关联字段 | 关系规则 |
| --- | --- | --- | --- |
| 客户 | 评级 | 客户编号 | 一个客户同一时点只能有一条有效评级 |
| 客户 | 额度 | 客户编号 | 一个客户同一时点只能有一条有效额度 |
| 额度 | 业务申请 | 额度编号、客户编号 | 一笔有效额度可发起多笔业务申请 |
| 业务申请 | 合同 | 业务申请编号 | 一笔申请对应一笔有效合同 |
| 合同 | 债项支用 | 合同编号 | 一笔有效合同可发起多笔支用 |
| 合同 | 押品 | 合同编号、押品编号 | 一个合同可关联多个押品，一个押品可按规则关联合同 |
| 债项 | 风险敞口 | 债项编号 | 一笔债项至少形成一条当前有效敞口记录 |
| 债项 | 逾期 | 债项编号 | 一笔债项可产生多期逾期记录 |
| 债项 | 债项违约 | 债项编号 | 满足规则时形成有效债项违约 |
| 债项违约 | 客户违约 | 客户编号 | 客户任一债项有效违约，则客户违约 |

### 4.2 组合风险监控流程

1. 系统按数据日期汇总有效风险敞口。
2. 按行业、产品、机构和客户计算 EAD、EL、压力 EL 和集中度。
3. 将实际值与有效限额及预警阈值比较。
4. 形成 NORMAL、WARNING、BREACH 或 DISABLED 状态。
5. 对预警和超限项目产生监测记录和管理提示。
6. 风险经理调整限额时，系统保存责任人、阈值、有效期和修改痕迹。

### 4.3 预警处置闭环

风险信号 → 预警案件 → 风险台账 → 整改任务 → 风险指标/风险事件 → 处置执行 → 案件关闭 → 效果观察 → 有效性评价 → 规则或模型反馈。

闭环要求：

- 风险评分达到预警门槛时可自动生成或刷新预警案件。
- 案件应自动关联客户风险台账和相关信贷数据。
- 案件启动后应生成整改任务并明确责任人、期限和措施。
- 处置状态变化应回写案件、台账、任务、指标和事件。
- 案件关闭后进入观察期，不得立即判定处置有效。
- 观察期结束后根据评分变化、逾期和违约情况形成效果评价。

### 4.4 模型治理流程

模型草稿 → 参数维护 → 样本模拟 → 提交审批 → 审批通过 → 发布生效 → 日常监控 → 回溯校准 → 调整或回滚。

### 4.5 AI 客户分析流程

输入客户编号或客户名称 → 查询本地信贷和风险数据 → 计算风险评分 → 形成证据链 → 按配置查询外部风险数据 → 合并但不降低本地风险结论 → 输出风险等级、主要信号、处置建议和数据来源。

## 5. 功能需求

### 5.4 风险台账

| 编号 | 功能需求 | 说明 |
| --- | --- | --- |

| B | 五级分类属于后三类，即次级、可疑或损失 |
| C | 评级等级为 21 |

同一债项满足多个条件时，应保留各条件标志，并按业务定义确定最终违约等级。客户维度只要存在一笔有效债项违约，即形成客户违约；全部债项治愈或关闭后，客户违约状态按审批规则更新。

### 6.5 数据一致性规则

| 编号 | 规则 |
| --- | --- |
| DR-001 | 所有核心业务编号必须全局或租户内唯一。 |
| DR-002 | 下游对象的客户编号必须与上游客户一致。 |
| DR-003 | 业务申请关联的额度必须有效且属于同一客户。 |
| DR-004 | 合同关联的申请、额度和客户必须一致。 |
| DR-005 | 债项支用日期不得早于合同生效日期。 |
| DR-006 | 逾期日期不得早于债项支用日期和应还日期。 |
| DR-007 | 违约日期不得早于业务事实发生日期。 |
| DR-008 | 已用额度、合同已支用金额和债项支用金额应按口径勾稽。 |
| DR-009 | EAD、EL、损失和回收金额不得为不合理负值。 |
| DR-010 | EL 平均值应能够由 PD、LGD 平均值和 EAD 解释；压力 EL 同理。 |
| DR-011 | 已删除记录不参与当前有效组合统计。 |
| DR-012 | 所有统计结果必须带数据日期，历史快照不得被当前结果覆盖。 |

### 6.6 数据生命周期

- 业务主数据采用逻辑删除，保留审计痕迹。
- 风险计算、模型回溯、限额快照和效果评价采用历史追加或按日期唯一的快照模式。
- 操作日志、审批日志和外部调用日志应按合规要求保留，建议不少于三年；生产环境最终期限由制度确定。
- 敏感身份、账户和联系方式字段应加密或脱敏保存。
- 测试数据不得使用未经脱敏的生产数据。

## 10. 安全与合规需求

### 10.1 数据分类

| 分类 | 示例 | 控制要求 |
| --- | --- | --- |
| 公开/普通 | 产品类型、通用状态字典 | 常规访问控制 |
| 内部 | 组合指标、风险报表、模型状态 | 登录和角色权限 |
| 敏感 | 客户联系方式、合同金额、评级、逾期和违约 | 最小权限、脱敏、导出审计 |
| 高敏感 | 法人证件号、银行账号、密钥和私钥 | 加密存储、严格授权、禁止日志输出 |

### 10.2 审计要求

- 登录、退出、失败登录和密码重置应审计。
- 用户、角色和权限变更应审计。
- 限额调整、模型提交审批发布回滚应审计。
- 预警案件启动、关闭、任务状态变化和效果评价应审计。
- 数据导出和外部数据查询应审计。
- 审计日志普通用户不得修改或删除。

### 10.3 合规边界

- AI 结论用于辅助风险识别，不作为自动审批依据。
- 外部数据使用范围应与合同、授权和隐私政策一致。
- 违约认定和模型阈值变更应经业务及模型治理审批。
- 监管口径与内部管理口径不一致时，应分别保存并明确标识。

## 15. 风险与应对

| 风险 | 影响 | 应对措施 |
| --- | --- | --- |
| 源系统数据口径不一致 | 指标无法勾稽 | 建立数据字典、口径负责人和质量检查 |
| 客户、合同、债项关联缺失 | 风险链路断裂 | 强制关联校验、异常清单和补录流程 |
| 模型样本不足 | 回溯偏差不稳定 | 标注样本量、设置最小样本门槛、延长观察期 |
| 限额初值不合理 | 大量误报或漏报 | 先观察后调整，保留历史和审批 |
| 外部数据质量不稳定 | AI 结论受干扰 | 本地结论优先、数据来源标识、熔断降级 |
| 预警关闭过早 | 虚假闭环 | 设置观察期并执行效果评价 |
| 权限配置过宽 | 敏感数据泄露 | 最小权限、定期复核和导出审计 |
| Docker 资源不足 | 服务启动或构建失败 | 资源基线、监控、分批构建和容量预留 |

## 附录 B：核心计算口径

- 组合 EAD = 有效风险敞口 EAD 求和。
- 组合 EL 平均值 = 有效风险敞口 EL 平均值求和。
- 组合 EL 衰退值 = 有效风险敞口 EL 衰退值求和。
- 加权 PD = Σ(EAD × PD) ÷ ΣEAD。
- 加权 LGD = Σ(EAD × LGD) ÷ ΣEAD。
- 集中度占比 = 分组 EAD ÷ 组合总 EAD。
- HHI = Σ(各分组集中度占比²)。
- 限额利用率 = 实际指标值 ÷ 限额值。
- 实际违约率 = 违约债项数 ÷ 观察债项数。
- 实际 LGD = 实际损失金额 ÷ 实际违约暴露。
- 处置评分变化 = 当前风险评分 - 关闭时风险评分。
